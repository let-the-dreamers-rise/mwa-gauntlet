### Describe the bug
A HELLO_REQ that is correctly signed with the association key but carries an invalid P-256 public key gets no HELLO_RSP, no session error and no termination. The connection is left in session establishment. Two variants:

- the point prefix is `0x05` instead of `0x04`
- the point is (1, 1), which is not on P-256

A HELLO_REQ with a bad *signature* does terminate the session (`onSessionError`), so invalid keys are handled differently from invalid signatures.

Cause: `ECDSAKeys.decodeP256PublicKey` throws `IllegalArgumentException` for a bad prefix, but `MobileWalletAdapterSession.parseHelloReq` only catches `UnsupportedOperationException`. For an off-curve point, decoding succeeds and the ECDH in `generateSessionECDHSecret` fails with an `UnsupportedOperationException` that nothing handles. Neither becomes a `SessionMessageException`.

Only a dapp holding the association key can send this, and the JCE provider did reject the off-curve point in my run, so this is about failing cleanly rather than key leakage. An explicit on-curve check still makes that independent of the provider, and `clientlib` uses the same decoder for HELLO_RSP.

### Expected vs actual behavior
Expected: the session is terminated, as for a HELLO_REQ with a bad signature.
Actual: no response and no termination; a later valid HELLO_REQ on the same connection is still answered.

### Suggested fix
Catch `IllegalArgumentException` as well in `parseHelloReq`. In `decodeP256PublicKey`, check that the point is on P-256 with coordinates below p. Turn an ECDH failure into a `SessionMessageException` in `handleSessionEstablishmentMessage`.

Full patch for this and the three related issues: https://github.com/let-the-dreamers-rise/mwa-gauntlet/blob/main/patches/public-fixes.patch. With it, the full `common`, `walletlib` and `clientlib` unit suites still pass.
